# Publishing FMCuttingBoard on the JetBrains Plugin Marketplace

Repository: [Blue-Kachina/fmcuttingboard](https://github.com/Blue-Kachina/fmcuttingboard)

FMCuttingBoard is already fairly close to publishable. It uses the IntelliJ Platform Gradle Plugin, has a stable plugin ID, builds a distributable ZIP, includes a custom SVG icon, and declares compatibility beginning with IntelliJ Platform 2024.2.

## Publishing checklist

### 1. Choose and add a software license

“Free to use” is not itself a software license.

JetBrains requires you to provide a Developer EULA or select an open-source license. For an open-source plugin, the Marketplace also requires a source-code link.

A permissive license such as **MIT** or **Apache-2.0** would likely suit this plugin. MIT is the simpler choice.

Add a root-level file named:

```text
LICENSE
```

Then mention it in `README.md`:

```markdown
## License

FMCuttingBoard is available under the MIT License. See [LICENSE](LICENSE).
```

When uploading the plugin, select the same license and provide the GitHub repository as the source-code URL.

Reference:

- [JetBrains Marketplace Approval Guidelines](https://plugins.jetbrains.com/docs/marketplace/jetbrains-marketplace-approval-guidelines.html)

### 2. Improve the Marketplace-facing metadata

Your current plugin ID is:

```xml
<id>dev.bluekachina.fmcuttingboard</id>
```

Keep this ID permanently. Changing it later would cause JetBrains to treat the plugin as a different plugin.

Your name, `FMCuttingBoard`, is acceptable. It is under JetBrains’ length limit and does not contain restricted naming terms such as “Plugin,” “IntelliJ,” or “JetBrains.”

Before publishing, ensure `plugin.xml` contains useful metadata similar to:

```xml
<idea-plugin>
    <id>dev.bluekachina.fmcuttingboard</id>
    <name>FMCuttingBoard</name>

    <vendor
```

Use an email address you are comfortable publishing publicly. Your Marketplace vendor profile should also contain a valid website and contact email.

### 4. Build and manually test the exact ZIP

On Linux or macOS:

```bash
./gradlew clean buildPlugin
```

On Windows PowerShell:

```powershell
.\gradlew.bat clean buildPlugin
```

The generated ZIP should appear under:

```text
build/distributions/
```

For the current version, it may be named something similar to:

```text
FMCuttingBoard-1.0.4.zip
```

Install that exact ZIP into a clean IDE instance:

```text
Settings
→ Plugins
→ gear icon
→ Install Plugin from Disk
```

Do not upload a ZIP of the GitHub repository. Upload the ZIP generated by the Gradle `buildPlugin` task.

### 5. Run JetBrains Plugin Verifier

JetBrains expects compatibility to be checked using Plugin Verifier.

With IntelliJ Platform Gradle Plugin 2.x, configure verification in `build.gradle.kts`, for example:

```kotlin
intellijPlatform {
    pluginVerification {
        ides {
            recommended()
        }
    }
}
```

Then run:

```bash
./gradlew verifyPlugin
```

Your repository currently uses an early 2.x release of the IntelliJ Platform Gradle Plugin. Consider updating it to a recent stable 2.x version before establishing your publishing workflow, since configuration and task behaviour have evolved.

Review verifier output carefully, especially for:

- IntelliJ internal API usage
- Missing classes
- APIs removed in newer IDE releases
- Java-version incompatibility
- Problems loading `plugin.xml`
- Incompatible extension registrations

Do not ignore warnings without first determining whether they affect supported IDE versions.

### 6. Sign the plugin

JetBrains provides plugin-signing support through the IntelliJ Platform Gradle Plugin.

A signing configuration generally looks like:

```kotlin
intellijPlatform {
    signing {
        certificateChain.set(
            providers.environmentVariable("CERTIFICATE_CHAIN")
        )
        privateKey.set(
            providers.environmentVariable("PRIVATE_KEY")
        )
        password.set(
            providers.environmentVariable("PRIVATE_KEY_PASSWORD")
        )
    }
}
```

Never commit the private key, certificate password, or other secrets to GitHub.

To create a signed artifact:

```bash
./gradlew signPlugin
```

When signing is configured, `publishPlugin` can also sign the plugin automatically before publishing.

Signing is separate from whether the plugin is free. It establishes the authenticity of the plugin and its updates.

Reference:

- [Publishing a Plugin](https://plugins.jetbrains.com/docs/intellij/publishing-plugin.html)

### 7. Create your JetBrains Marketplace vendor account

Sign in to JetBrains Marketplace with your JetBrains account and choose **Upload plugin**.

For the first upload, expect to:

1. Accept the Marketplace Developer Agreement.
2. Create a vendor profile.
3. Declare trader or non-trader status for EEA requirements.
4. Supply valid vendor contact information.
5. Select the plugin license.
6. Provide the source-code URL.
7. Choose appropriate categories or tags.
8. Upload the generated plugin ZIP.

You do not need banking information for a free plugin. Payment information applies to paid or freemium plugins.

Use the default stable release channel unless the version should be considered experimental.

The first plugin version normally needs to be uploaded manually.

### 9. Be clear about clipboard and platform behaviour

Because the plugin reads and writes system clipboard data, state this clearly in the listing.

The project also appears to use JNA as a Windows clipboard fallback. Document:

- Whether Windows is the only fully supported platform
- Whether macOS and Linux have been tested
- Whether clipboard content ever leaves the computer
- Whether the plugin performs network communication
- Whether telemetry or analytics are collected

When everything remains local and no data is collected, say so directly.

For example:

> FMCuttingBoard processes clipboard content locally. It does not transmit clipboard data, collect analytics, or communicate with an external service.

A formal privacy policy may be required when personal data is collected or transmitted. Even when no data is collected, a clear privacy statement improves transparency.

## Future release automation

After the initial version is accepted, future releases can be automated using:

- A JetBrains Marketplace permanent token
- Gradle’s `publishPlugin` task
- GitHub Actions secrets
- A release workflow triggered by tags or GitHub releases

JetBrains recommends keeping the publishing token outside the repository, commonly as a GitHub Actions secret exposed to Gradle through:

```text
ORG_GRADLE_PROJECT_intellijPlatformPublishingToken
```

A typical future release process could be:

1. Update the plugin version.
2. Update release notes.
3. Run tests.
4. Run Plugin Verifier.
5. Build the plugin.
6. Sign the plugin.
7. Publish to a test channel.
8. Promote or publish to the stable channel.
